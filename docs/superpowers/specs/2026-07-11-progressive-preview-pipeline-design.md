# PureWall 渐进式大图预览管线设计

**日期：** 2026-07-11
**状态：** 已批准
**范围：** 启动活动图恢复、缩略图/大图派生、任务调度、缓存与前端呈现

## 1. 背景与问题

PureWall 当前把 512 px 缩略图和 1440 px 大图预览作为两个独立媒体任务。任务按 `(kind, path)` 去重，因此同一张超大图片可以同时执行两次完整解码。四个共享工作线程如果已经被缩略图占满，后到的大图即使队列优先级更高也无法抢占。

实际库中存在 90–112 MP、75–105 MiB 的图片。与当前 Rust `image` 管线等价的 release 测量显示，单张大图派生约需 2.1–3.4 秒；debug 构建更慢。当前缓存中 245 张壁纸只有 39 张命中现用大图 profile，冷启动体验不能依赖“现场生成很快”。

另一个功能性错误是前端启动时没有调用已有的 `read_current_wallpaper_path_cmd`。`currentWallpaperPath` 初始为空，画廊分页完成后会把第一张记录当作活动壁纸，因此页面可能先加载错误的大图，真正当前壁纸也没有得到最早预热。

## 2. 目标与验收标准

### 2.1 用户体验目标

1. 应用启动后先恢复 Windows/PureWall 持久化的真实当前壁纸，再决定活动图。
2. 当前壁纸的大图预览拥有最高优先级，并在每次壁纸切换后主动生成和持久缓存，使下一次进入页面通常零等待。
3. 大图缓存命中时，活动区首帧直接使用大图；冷缓存时立即显示已有 512 px 缩略图，生成完成后原位渐进替换，不出现空白或布局跳动。
4. 画廊缩略图工作不能长期阻塞活动大图。
5. 同一源文件在任意时刻最多进行一次解码，不允许缩略图和预览重复解码。
6. 不在启动阶段预生成整个图库的大图，避免数分钟 CPU/磁盘抖动。

### 2.2 工程验收标准

- 启动 bootstrap 在画廊分页前确定 `currentWallpaperPath` 和 `activeWallpaperPath`。
- 缓存命中的大图命令只做路径验证和返回，不执行图像解码。
- 队列以规范化源路径为唯一键；追加 preview 需求会升级已有 thumbnail 请求。
- 至少保留一条大图可用执行通道，缩略图积压不能占满全部媒体能力。
- Windows 预览派生优先使用 WIC 目标尺寸解码；不支持的格式或 WIC 失败时回退到 `image`。
- 对队列升级、启动恢复、缓存命中、回退路径和大图优先级建立自动化回归测试。
- release 性能基准记录 20–25 MP 与 90–112 MP 样本的解码/缩放/编码耗时；不把 debug 图像速度当作发布性能。

## 3. 方案概览

```text
应用启动
  -> 安装媒体事件监听
  -> bootstrap 当前壁纸
       -> 大图命中：立即返回 cache path
       -> 大图未命中：返回缩略图（若有）并提交最高优先级 preview 请求
  -> 首屏活动区稳定显示
  -> 并行加载画廊第一页
  -> 空闲时仅预热有限的近期候选

媒体请求(path, needs)
  -> 按规范化 path 合并/升级
  -> preview lane 优先领取含 preview 的请求
  -> 一次目标尺寸解码
  -> 生成所需派生文件
  -> 原子写入缓存
  -> 发出 derivative-generated 事件
```

## 4. 启动 bootstrap 与主动预热

新增单一启动命令 `bootstrap_active_wallpaper`，返回：

- `path`: 持久化当前壁纸路径；不存在或已失效时为空。
- `thumbnail_path`: 已存在的缩略图缓存路径，可空。
- `preview_path`: 已存在的大图缓存路径，可空。
- `preview_state`: `ready | queued | unavailable`。

前端必须先安装媒体事件监听，再调用 bootstrap，消除“生成事件先于监听器”的竞态。bootstrap 只允许做轻量数据库/文件检查；缺少大图时只排队，不同步解码。

如果当前路径有效，前端立即同时设置 `currentWallpaperPath` 与 `activeWallpaperPath`。随后画廊第一页加载不再覆盖该选择；即使当前壁纸不在第一页，活动区仍能根据 bootstrap 返回的缓存路径展示它。

所有成功改变系统壁纸的入口——主界面、自动轮换、托盘、桌面小组件和 CLI action——都必须调用同一个 `prewarm_active_preview(path)` 边界。这样大图派生发生在“壁纸刚切换、用户尚未重新进入主页面”的时间窗口，而不是等页面打开才开始。

启动只预热当前壁纸。当前预览完成且系统空闲后，可以限量预热下一轮候选或可视区域少量图片；首版上限为 2 张，且任何新的活动预览请求都会压过或取消未开始的推测预热。禁止启动时扫描并生成全库大图。

## 5. 按源路径合并的媒体请求

将 `MediaJobKind` 的两个独立任务改为一个路径级请求：

```rust
struct MediaNeeds {
    thumbnail: bool,
    preview: bool,
}

struct MediaJob {
    path: String,
    needs: MediaNeeds,
    priority: MediaPriority,
}
```

队列内部维护每个规范化路径的 `queued | running` 状态和待生成 needs：

- thumbnail 后追加 preview：升级同一 queued job，并移动到活动预览队首。
- preview 后追加 thumbnail：合并需求，不新增第二次解码。
- 任务运行中追加另一派生需求：记录 pending needs；工作线程完成当前解码前再次读取状态，能复用解码结果则同批输出，否则完成后只补缺失派生，但不得与该路径并发。
- 同一路径重复请求相同派生：幂等，无新任务。

优先级从高到低：当前活动预览、用户新选择预览、普通预览、可视缩略图、推测预热。较新的用户选择高于旧选择。

## 6. 工作线程与内存边界

首版使用三条媒体执行通道：

- 1 条 preview-reserved lane：只领取包含 preview 的请求。
- 2 条 general lane：优先 preview，其次 thumbnail。

这样即使 general lane 正在处理超大缩略图，活动大图仍有可用通道。相比当前四个线程同时完整解码 100 MP 图片，三线程和路径级去重也降低峰值内存。具体线程数集中为配置常量，并以真实样本测量后再调整。

队列继续保持缩略图 backlog 上限；未开始的推测预热允许直接丢弃。运行中的解码不做危险的强制中断，但任务提交后可通过 generation token 忽略已经过时的前端展示结果。

## 7. Windows WIC 目标尺寸解码

Windows 平台新增独立的 `image_decoder`/`windows_image_decoder` 深模块：输入源路径、目标边长和输出参数，输出编码后的派生文件或明确的可回退错误。

优先尝试 WIC decoder 的 `IWICBitmapSourceTransform` 请求目标尺寸；decoder 不支持 transform 时使用 WIC scaler；仍失败或格式不支持时回退现有 `image` 管线。WIC/COM 资源只存在于 Rust 后端，不向 Vue 暴露平台细节。

缩略图目标保持 512 px，大图目标保持 1440 px，首版不改变视觉规格，以便把性能变化和画质变化分开验证。编码先保持 JPEG q88/q92；后续若评估 AVIF/WebP，另立决策。

## 8. 缓存策略

- WebView 继续只访问 PureWall 自有 derivative cache，不扩大到任意用户源目录。
- 文件先写临时路径，成功后原子替换，避免 WebView 读到半文件。
- cache key 至少包含规范化源路径、源文件修改时间/大小、派生类型和格式版本。
- 普通质量参数调整不随意更换格式版本，防止已有大图集体冷失效。
- 必须升级格式版本时，允许把最近一个可验证的旧版派生作为临时 fallback，并在后台 stale-while-revalidate；新派生完成后再替换。
- 缓存清理保护当前壁纸、活动壁纸和有限的近期预热项。

## 9. 前端呈现状态

活动预览使用显式状态机，而不是仅靠 URL 是否存在：

- `idle`: 没有有效活动图。
- `thumbnail`: 显示低清 fallback，大图正在排队/生成。
- `preview`: 显示完整大图。
- `error`: 保留缩略图并展示非阻断错误提示。

`CurrentWallpaperPanel`、`InspectorPanel` 和 `QuietCanvas` 统一消费同一个活动媒体状态。大图主体优先使用真实 `<img>`，以获得浏览器解码、缓存、`load`/`error` 事件和可测量的切换时机；装饰性背景可以继续用 CSS，但不能各自发起独立预览请求。

大图 URL 只有在新 `<img>` 已触发 `load` 后才替换当前展示，避免从清晰图切换到短暂空白。路径切换使用 generation token，忽略旧图片晚到的事件。

## 10. 错误处理与可观测性

派生失败事件包含 `path`、`derivative`、`backend`（WIC/image）和用户可读摘要，不包含大段二进制或敏感目录枚举。失败不会清掉已显示的缩略图。

debug 日志记录 cache hit/miss、排队等待、decode、resize、encode、总耗时和回退原因；release 默认只保留失败与慢任务阈值日志。计时不得持有数据库全局锁。

## 11. 测试策略

严格按 RED → GREEN → REFACTOR 实施：

1. 队列单元测试：同路径升级、运行中合并、最新活动图优先、reserved lane、backlog 丢弃与 shutdown。
2. bootstrap 单元/集成测试：恢复持久化路径、失效路径、缓存命中、冷缓存只排队、第一页不得覆盖当前选择。
3. decoder 合同测试：目标尺寸、方向、原子写入、WIC 失败回退、源文件变更导致 cache miss。
4. 前端状态测试：缩略图立即展示、大图 load 后替换、旧事件被忽略、错误保留 fallback。
5. 性能验证：固定真实样本在 release 下记录耗时和峰值并发，不设置依赖单台机器绝对速度的脆弱单元断言。

## 12. 分阶段交付

### 阶段 A：启动正确性与无空白体验

先修复当前壁纸恢复顺序，统一活动媒体状态，并在所有壁纸切换入口主动排队大图。此阶段就能让已有大图缓存真正被首帧使用，冷缓存用缩略图稳定过渡。

### 阶段 B：路径级去重与预览保留通道

重构媒体队列，消除同源重复解码并确保活动预览不被缩略图饿死。

### 阶段 C：WIC 目标尺寸解码

接入 Windows 原生目标尺寸解码与 `image` fallback，用真实超大图片做 release 性能验证。

### 阶段 D：有限预测预热与缓存治理

只在阶段 A–C 稳定后加入最多 2 张候选预热、旧版本 fallback 与缓存清理策略，防止“优化启动”演变为后台全库转码。

## 13. 非目标

- 不把原始壁纸目录直接开放给 WebView asset protocol。
- 不在启动时生成全库大图。
- 不同时更换派生尺寸、编码格式和 UI 布局。
- 不把 debug 构建的图像处理时间作为发布版性能结论。
- 本设计不包含目录同步、加权随机、批量导入事务和删除一致性修复；这些在预览管线稳定后按原审查计划继续。
